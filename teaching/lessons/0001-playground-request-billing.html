Playground 不是另一套模型调用

它是一个用户态入口，最后汇入统一 Relay。掌握这条主链，你就能开始在项目里做有边界的 vibe coding。

今天的一个胜利

读完后，你应该能回答：用户在 Playground 点一次发送，为什么既能调用上游模型，又会正确扣除用户额度？

先看全景

React: PlaygroundInput -> useChatHandler
↓ POST /v1/chat/completions
Gin: TokenOrUserAuth + SetupSessionRelayContext + Distribute
↓
SetupSessionRelayContext: 用户会话 -> 虚拟 playground Token
↓
controller.Relay: 校验 -> 估算 -> 价格 -> 预扣 -> 上游
↓
PostTextConsumeQuota: usage -> 实际 quota -> 结算 -> 日志

三个关键节点

1. 前端只负责发起和展示

Playground 组合状态、选项、聊天和输入组件。useChatHandler 根据 config.stream 选择流式或普通请求。请求体由 buildChatCompletionPayload 构造，流式响应只更新界面，不负责计费。

2. 标准 Relay 负责接入用户会话

/v1/chat/completions 先走 TokenOrUserAuth，随后由 SetupSessionRelayContext 将用户会话适配为统一 Relay 所需的虚拟 Token 上下文。请求体中的 group 只能选择用户可用分组，最后进入 Relay(OpenAI)。

设计要点：虚拟 Token 是复用 Token 上下文的适配层，不是持久化 API Key。这样 Playground 可以复用分组、模型、渠道选择和计费代码。

3. 计费是预扣再结算

Relay 先估算输入 tokens，ModelPriceHelper 得到预扣额度，然后调用 PreConsumeBilling。上游返回真实 usage 后，PostTextConsumeQuota 计算实际额度并调用 SettleBilling：补扣差额或返还多扣部分。失败则 defer 触发 Refund。

预扣 = 根据估算 usage 先锁定额度
实际 = 根据上游返回 usage 计算
结算 = 实际 - 预扣
失败 = 退回尚未结算的预扣

对于 Playground，RelayInfo.IsPlayground 会让 BillingSession 跳过真实 Token 额度调整，但钱包或订阅资金来源仍然参与计费。

用源码练习一次定位

  1. 打开 router/relay-router.go 和 middleware/auth.go，找出会话请求进入统一 Relay 的两个中间件。
  2. 打开 controller/relay.go，找出预扣费调用和失败退款所在的两个位置。
  3. 打开 service/text_quota.go，找出上游 usage 进入结算的位置。

心中填空：入口是 ____；预扣是 ____；实际结算是 ____；失败退款是 ____。
